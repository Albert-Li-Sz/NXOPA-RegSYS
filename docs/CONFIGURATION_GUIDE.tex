\section{首次部署与管理员初始化}
\textbf{一键安装。}宿主机准备 Docker、Compose 2.24.4 以上、Bash、curl 和 OpenSSL。下载根目录的统一脚本，自动下载并校验发布包；也可解压 Release 安装包后直接运行其根目录脚本：
\begin{Code}
curl -fsSL https://raw.githubusercontent.com/Albert-Li-Sz/NXOPA-RegSYS/main/install.sh -o install.sh
bash install.sh
curl --fail http://127.0.0.1:8080/api/v1/health
\end{Code}
默认目录为 \code{/opt/nxopa-regsys}，可用 \code{--dir} 指定其他目录。向导默认拉取预构建镜像，完整源码也可构建。自动生成权限为 600 的 \code{deploy/.env}，服务健康后创建首次管理员；已有配置与密钥保留，宿主机无需 Node.js 或 pnpm。内部 Caddy 提供本机 HTTP 入口，默认 8080，由自有反向代理负责公网 HTTPS。健康接口应返回 \code{status: ok}，上线前还须检查代理下的健康接口与登录。安装镜像使用完整固定版本标签，并按 Docker 服务端选择平台；新入口转换旧包的自动摘要覆盖，保留下载校验。

\textbf{更新与卸载。}不带参数显示安装、更新、卸载和状态菜单，也可在实际安装根目录分别执行：
\begin{Code}
bash install.sh update
bash install.sh uninstall
\end{Code}
更新先加密备份，再下载新版材料、拉取或构建、迁移并等待健康检查；备份失败中止操作。默认卸载保留数据，永久删除须准确输入 \code{DELETE 项目名}。配置和备份保留，备份解密需要原加密密钥。旧版 \code{install/.env} 自动复制到 \code{deploy/.env}，保留项目名、数据库密码、加密密钥与代理模式。维护命令见 \code{bash install.sh --help}。

\textbf{设置访问地址。}向导保存下列部署项；也可编辑 \code{deploy/.env}。自行完成域名解析、证书与代理配置，参考 \code{deploy/nginx.conf.example}。首次启动使用环境地址作为初始值；登录后在“管理中心 → 全局设置”维护邮件与邀请链接使用的地址。
\begin{Code}
PUBLIC_URL=https://contest.example.org
REVERSE_PROXY_MODE=gateway
GATEWAY_PORT=8080
GATEWAY_BIND_ADDRESS=127.0.0.1
ALLOW_PRIVATE_INTEGRATIONS=true
\end{Code}
外层代理将整个站点转发到 \code{http://127.0.0.1:8080}，保留路径、Host 和原始协议；内部 Caddy 分流前端与 API。默认不占用公网 80 / 443、不申请证书。旧配置升级保留原代理模式。安装入口使用 \code{PUBLIC_URL}；旧根目录 Compose 使用 \code{DEPLOY_PUBLIC_URL}。内网联动默认开启，显式设置 false 可禁止私有地址；正式环境外部评测接口要求 HTTPS。

\textbf{需要留在部署环境的配置：}数据库、缓存、私有文件目录和 \code{ENCRYPTION_KEY}。这些属于运行基础设施。额外信任来源可在后台维护，环境变量也可保留恢复入口。保留同一个加密密钥，否则无法解密已有邮件密码、评测凭据与备份。

\textbf{可在管理中心调整的配置：}站点名称、主色、页脚、公网地址、邮件服务、用户授权、评测平台、接口令牌、全局字段和准考证模板。首次登录后优先完成邮件配置，以便用户验证邮箱和找回密码。

\section{首页、登录与站点设置}
首页 \code{/} 独立展示系统介绍。未登录时点击“进入报名系统”，会跳转登录；直接访问竞赛列表或竞赛详情也会触发登录检查。登录成功后返回原本准备访问的页面，包括详情页参数。
\shot[0.31\textheight]{02-login}{登录入口：使用本站用户名或邮箱与密码。}

系统管理员登录后打开“管理中心 → 全局设置”，调整站点名称、主色与页脚，并点击“保存”。竞赛管理员没有全局设置权限。默认主色为 \texttt{\#2080F0}。
\shot[0.24\textheight]{04-site}{全局设置中的站点配置。}

\textbf{公网地址与信任来源。}公网地址用于生成邮件和邀请链接。同源请求与当前公网地址自动允许。系统管理员点击“编辑”，在“信任的请求来源”每行填写一个内外网根地址，也可用逗号分隔，保存后立即生效。例如 \code{https://reg.example.org} 与 \code{http://192.168.1.10:8080}。地址须包含协议及端口（如有），不接受通配符、账号密码、额外路径、查询参数或片段。环境变量 \texttt{TRUSTED\_\allowbreak MANAGEMENT\_\allowbreak ORIGINS} 继续可用，并在后台单独展示。保存检查版本并记录审计；TLS、域名及访问控制由反向代理负责。

\newpage
\begin{enumerate}
\item 域名解析：给注册域名添加指向服务器的 A 记录；启用 IPv6 时再配置正确的 AAAA 记录。
\item 反向代理：默认由自有代理监听 HTTPS，配置证书。整个站点转发到内部 Caddy 的 \code{127.0.0.1:8080} HTTP 入口，保留 Host、Origin 和请求协议。
\item 更换域名：先解析新域名、配置代理与证书，并实际检查新站可登录，再保存新的公网地址。旧的、已经发出的邀请 URL 不会被重写，迁移期保留旧域名反向代理或引导用户重新获取链接。
\item 请求与会话：登录前亦检查写请求来源，登录后另检查 CSRF 令牌。反向代理正确传递 \texttt{X-\allowbreak Forwarded-\allowbreak Proto}。HTTPS 入口使用 Secure 会话 Cookie；公网 HTTPS 与内网 HTTP 并用时，将内网 HTTP 根地址显式加入信任来源，该入口才可使用适合 HTTP 的会话 Cookie。
\end{enumerate}
\begin{Code}
# 原生部署：在项目目录使用原数据库与加密密钥
pnpm restore:public-url https://reg.example.org
# Docker：在 API 容器内恢复数据库配置
docker compose exec api pnpm restore:public-url https://reg.example.org
\end{Code}
恢复命令保留站点其他设置、递增版本并记录审计，不需要清空数据库。


公开邮箱注册保留；用户验证邮箱并完善五项资料后才可报名，授权邀请仍需明确确认。本站账号密码与评测平台比赛账号的密码分别管理。

\section{GitHub 登录与账号资料}
系统管理员打开“管理中心 → GitHub 登录”。在 GitHub 开发者设置新建 OAuth App，填写站点首页与后台显示的回调地址，再把 Client ID、Client Secret 填入本站并启用。回调路径固定为 \code{/api/v1/auth/github/callback}；自定义回调地址需要与 GitHub 配置一致。
\shot[0.48\textheight]{27-github-settings}{GitHub 登录配置：回调地址、启用状态和凭据。空白密码框表示保留已保存密钥。}

参考\href{https://github.com/nextauthjs/next-auth/blob/main/packages/core/src/providers/github.ts}{Auth.js 开源 GitHub Provider}与\href{https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps}{GitHub 官方 OAuth 流程}。使用一次性 state 与 PKCE；Client Secret 加密保存，GitHub 令牌不写入数据库。

\newpage
启用后登录页显示“使用 GitHub 登录”。首次授权取得 GitHub 已验证邮箱后创建本站账号；未验证邮箱不能登录。已有相同邮箱账号不会自动合并，先用本站账号登录，在账号中心点击“绑定 GitHub”。只使用 GitHub 登录的账号先通过邮箱找回流程设置本站密码，再解除绑定，避免失去登录方式。
\shot[0.40\textheight]{24-github-login}{登录页同时提供本站账号与 GitHub 登录入口。}

GitHub OAuth App 的真实凭据由部署管理员配置。本版本以独立模拟 GitHub 服务测试授权、令牌交换、已验证邮箱、重复 state、绑定和同邮箱冲突，并未替管理员建立真实 OAuth App。

\newpage
\textbf{报名所需账号资料。}邮箱注册或 GitHub 登录后，在账号中心填写学号、姓名、班级、学院和性别。姓名保存在账号姓名字段，其他四项保存在个人资料；五项全部有效才允许创建或提交报名。旧账号缺项时补充后可继续报名，原报名与历史快照保留。
\shot[0.54\textheight]{26-profile}{账号中心的五项必填资料。填写完成并保存后，返回原报名页面。}

注册完成后直接引导补充资料；已登录用户从竞赛点击报名时也会检查。团队中已绑定本站账号的参赛成员分别完善资料；指导老师资料仍按竞赛规则填写。

\section{邮件服务：保存、检测与实际收件}
打开“管理中心 → 邮件设置”。只有系统管理员可以查看、修改或测试邮件配置。未在后台保存时，使用部署环境中的初始 SMTP 配置；后台保存后优先使用数据库配置，无需重启 API 或后台任务服务。
\shot[0.47\textheight]{03-mail}{本地邮件测试示例：保存配置，检测连接，再向当前管理员发送测试邮件。}

\begin{tabularx}{\linewidth}{@{}lX@{}}\toprule
配置项 & 填写方法\\\midrule
服务器地址 / 端口 & 填服务商的 SMTP 主机名，不含协议与路径；端口按服务商要求填写。\\
连接加密 & 465 通常用“加密连接”；587 通常用“连接后升级加密”。按服务商文档确认。\\
服务器认证 & 通常启用。填写服务商用户名及密码或邮箱授权码。\\
发件邮箱 / 名称 & 使用服务商允许的发件地址；名称建议填写系统名称。\\\bottomrule
\end{tabularx}

先保存，再“检测连接”，最后“发送测试邮件”。测试邮件只发给当前管理员。任务成功后还应检查实际收件箱或垃圾邮件；连接检测通过不能单独证明邮件可送达。加密方式对应关系见\href{https://nodemailer.com/smtp}{官方邮件配置说明}。

密码加密保存且不返回浏览器。编辑时留空保留原密码；更换认证用户名时重新填写密码。关闭服务器认证并保存，会清除认证密码。关闭邮件服务后不能发送验证和找回邮件，失败任务会保留原因供管理员处理。

\section{通过链接授予账号身份}
打开“管理中心 → 用户权限”，点击“生成邀请链接”。选择邀请类型、已有账号或受邀邮箱；竞赛管理员还需选择授权竞赛。默认有效期为 7 天，可设置 1 至 30 天。
\shot[0.55\textheight]{05-role-invitation}{生成竞赛管理员授权链接的配置表单。}

\begin{enumerate}
\item 点击“生成链接”并复制 URL，交给指定接收者。链接只在生成时展示。
\item 接收者通过该 URL 登录或注册指定邮箱，完成邮箱验证。
\item 接收者在邀请页面查看身份和竞赛范围，点击“确认接受”后授权才生效。
\end{enumerate}
仅生成或打开链接不会增加权限。账号邀请不附加管理员权限；系统管理员、竞赛管理员、指导老师身份分别邀请。撤销未确认邀请立即使链接失效；撤销已有角色后，旧链接不能重新恢复权限。

\newpage
\textbf{用户标签与筛选。}在“用户权限”列表点击“编辑标签”，输入或选择标签并保存，例如“集训队”“2026级”。每个账号最多 20 个标签，单个标签最多 40 字；重复值自动合并。标签只用于管理筛选，不授予权限。
\shot[0.48\textheight]{25-user-tags}{管理员用户列表展示标签，并可按标签筛选。}

用户列表可按标签筛选；竞赛管理员可在报名列表按成员标签筛选。列表、统计与 CSV 导出采用相同筛选条件。更新标签检查版本，冲突时刷新后重新保存。

\section{授权确认与范围检查}
\shot[0.46\textheight]{06-role-confirmation}{接收者确认前查看身份、受邀邮箱、有效期和指定竞赛。}

确认后刷新管理中心，竞赛管理员应只看到获得授权的竞赛，并可处理对应报名、财务、工单和准考证。竞赛管理员不能修改全站 SMTP 设置或评测实例的接入凭据。

指导老师身份也通过邀请确认。老师与某份报名的关联还需通过链接确认，关联解除后立即失去该报名的访问和代办权限。队伍成员邀请保持独立确认流程；竞赛选择“队长代填”时按照竞赛规则录入人员信息。

\textbf{排查常见问题}
\begin{itemize}
\item 邮箱不匹配：使用邀请指定邮箱登录，不能由其他账号接受。
\item 邮箱未验证：到账号中心重新发送验证邮件，再返回邀请页面。
\item 链接过期或撤销：由系统管理员生成新的邀请。
\item 权限范围不符：检查是否选中了正确竞赛，以及身份是否已经被撤销。
\end{itemize}

\section{接入 Hydro 评测平台}
Hydro 接入使用 \code{hydro-contest-center} 插件，当前插件 0.2.1 适配 Hydro 5.0.7。下载入口位于\href{https://albert-li-sz.github.io/NXOPA-RegSYS/#hydro-plugin}{教程网页的 Hydro 插件下载区}；同时提供版本化安装包、稳定入口和 SHA-256。安装前核对包名、版本与摘要。不要把实例 Token 写入安装包。
\begin{Code}
curl -fLO https://albert-li-sz.github.io/NXOPA-RegSYS/downloads/hydro-contest-center-0.2.1.tgz
curl -fLO https://albert-li-sz.github.io/NXOPA-RegSYS/downloads/hydro-contest-center-0.2.1.tgz.sha256
sha256sum -c hydro-contest-center-0.2.1.tgz.sha256
# macOS 也可用 shasum -a 256 比对网页摘要
npm install --prefix /opt/hydro hydro-contest-center-0.2.1.tgz
\end{Code}
\textbf{原生部署。}确认运行 Hydro 的用户、工作目录和 addon.json 所在位置。以 Hydro 运行用户安装到其 Node.js 工作目录，将安装后的插件目录添加到该用户的 \code{~/.hydro/addon.json}，保留原有其他插件。项目提供的包只含源码、说明和许可证。
\begin{Code}
["@hydrooj/ui-default", "/opt/hydro/node_modules/hydro-contest-center"]
\end{Code}
设置 \code{CONTEST_CENTER_TOKEN} 为至少 32 位的随机密钥，本站与 Hydro 必须使用同一值；设置域白名单 \code{CONTEST_CENTER_DOMAINS=system,training}。这些变量必须进入 Hydro 进程环境；只在登录终端中 export 不会改变已运行的 systemd／PM2 服务。
\begin{Code}
# systemd 服务的 EnvironmentFile 示例（权限 600）
CONTEST_CENTER_TOKEN=replace_with_at_least_32_random_characters
CONTEST_CENTER_DOMAINS=system,training
# 修改服务的 EnvironmentFile 或 Environment 后
sudo systemctl daemon-reload
sudo systemctl restart hydro
# PM2 修改进程环境后
pm2 restart hydro --update-env
\end{Code}
\textbf{Docker 部署。}在自己的 Hydro 镜像中安装下载包，或将插件目录只读挂载到容器，再更新容器内实际运行用户的 addon.json。Token 与域白名单放入 Compose 的 environment 或受保护环境文件，重建／重启容器使变量进入进程；不要仅修改宿主机文件后假定容器已生效。
\begin{Code}
# 自有镜像示例，基底应与自己的 Hydro 部署一致
COPY hydro-contest-center-0.2.1.tgz /tmp/bridge.tgz
RUN npm install --prefix /opt/hydro /tmp/bridge.tgz && rm /tmp/bridge.tgz
# Compose 相应服务
# environment:
#   CONTEST_CENTER_TOKEN: ${HYDRO_BRIDGE_TOKEN}
#   CONTEST_CENTER_DOMAINS: system,training
docker compose up -d --build hydro
\end{Code}
\shot[0.40\textheight]{07-hydro-instance}{本站后台的 Hydro 实例配置，密钥不展示。}

\textbf{获取域和比赛编号。}打开目标比赛，地址由平台基址、\code{/d/training/contest/} 与 24 位比赛编号组成，例如：
\begin{Code}
https://hydro.example.org/d/training/contest/0123456789abcdef01234567
\end{Code}
域为 \code{training}，比赛编号为最后的 24 位标识。默认域可能省略 \code{/d/system}，此时填 system。比赛必须已存在，白名单必须包含所选域。
\shot[0.32\textheight]{15-hydro-contest}{独立 Hydro 5.0.7 实例的实际比赛页，可从地址栏获取比赛编号。}

\textbf{完整配置示例。}实例名称“社团 Hydro 评测平台”、地址 \code{https://hydro.example.org}，类型 Hydro；选择可使用的本站竞赛。在比赛绑定填域 training、目标比赛 24 位编号，启用昵称映射、同步非正式报名，参赛性质选择“跟随报名性质”。队伍名称写入目标域昵称；个人报名使用姓名。独立比赛用户名与密码由本站生成，不复制本站密码。

非正式报名经管理员审核后，在比赛内写入 \code{unrank=true}；正式报名写入 false。“全部作为非正式参赛”覆盖两类报名的远端性质。“不导入非正式报名”则跳过该类报名并明确显示状态。插件探测应返回版本 0.2.1 及昵称、非正式、比赛关联能力；旧插件缺失能力时提示升级。

\textbf{验收与故障排查。}依次探测、提交／审核报名、查看任务、领取比赛账号、实际登录目标比赛；核对域昵称与比赛状态，再重复同步确认远端用户编号不变。Hydro 的昵称属于域用户资料，某些排行榜视图按原平台权限隐藏昵称；不要为了显示昵称给所有用户开放私人资料权限。
\begin{itemize}
\item 401／403：检查 Token 一致、域在白名单中、进程确实收到环境变量；不在浏览器或日志中展示完整密钥。
\item 404：检查反向代理是否保留插件路径、插件是否安装并启用；确认域和比赛编号。
\item 能探测但无法导入：检查目标比赛是否存在、报名是否有资格、昵称是否为空，以及账号是否被其他报名占用。
\item 修改资料后：重新提交和审核，再生成新版本同步任务。旧任务版本不符时不能直接重试覆盖新资料。
\end{itemize}

\section{接入 DOMjudge 评测平台}
当前适配目标版本为 DOMjudge 9.0.1。本站通过该版本的 REST 写接口创建学校、队伍和账号，CCS 读接口用于确认组织、分组、比赛关联与账号访问；不只创建独立账号。
\begin{enumerate}
\item 以 DOMjudge 管理员登录后台，创建目标比赛，确认启用时间、开始／结束时间及允许参赛的分组。
\item 新建独立 API 服务账号，授予 \code{api_reader} 与 \code{api_writer}；不要把管理员登录账号当作长期服务凭据。原生部署填写实际 HTTPS 基址；Docker 对外使用配置好的反向代理 HTTPS 地址，容器内部 host 名不能直接用于公网访问。
\item 在本站“管理中心 → 评测平台”添加实例，填写中文名称“社团 DOMjudge 评测平台”、地址 \code{https://domjudge.example.org} 和 API 用户名／密码，授权指定本站竞赛。
\end{enumerate}
\shot[0.39\textheight]{08-domjudge-instance}{本站 DOMjudge 实例配置，服务密码不展示。}
\shot[0.32\textheight]{16-domjudge-users}{独立 DOMjudge 9.0.1 后台：服务账号与比赛队伍账号分别管理。}

\textbf{获取外部 ID。}不要把数据库数字主键和接口外部 ID 混用。使用 API 服务账号请求 \code{/api/contests}、\code{/api/organizations} 与 \code{/api/contests/<比赛ID>/groups}，读取 JSON 中 id；本站绑定填这些外部 ID。用下面命令交互输入 API 密码，避免在命令历史里保存密码。
\begin{Code}
curl --user reg_bridge https://domjudge.example.org/api/contests
curl --user reg_bridge https://domjudge.example.org/api/organizations
curl --user reg_bridge https://domjudge.example.org/api/contests/training-2026/groups
\end{Code}
\textbf{正式与非正式分组。}建立例如 \code{official}（正式队伍，排名顺序 0）和 \code{unofficial}（非正式队伍，排名顺序 1），在目标比赛允许这两个组。不同排名顺序将分别排名；相同顺序会合并排名，因此不能只改分组名称。是否隐藏分组由主办方决定；在目标比赛的奖牌／奖项配置里按分组设置，非正式组按比赛要求不设置正式奖项。本站不自动修改远端奖项。
\shot[0.32\textheight]{17-domjudge-groups}{DOMjudge 目标比赛分组：正式与非正式参赛使用不同排名顺序。}

\textbf{完整绑定示例。}目标比赛 \code{training-2026}，正式组 \code{official}，非正式组 \code{unofficial}，策略“跟随报名性质”，同步两类报名。历史报名缺少学校资料时可填写默认组织编号；新报名使用“代表学校／单位”并经学校映射确认，不用成员个人学校替代。

\textbf{学校确认流程。}未知学校允许提交报名；取得资格后显示“等待学校确认”。管理员打开绑定的“学校映射”：选择已有远端组织，或核对全称、简称、国家三位代码（中国 CHN）与可选 ICPC 编号后确认创建。确认后继续原报名的同步，不需要重新报名。学校外部 ID 使用稳定标识，失败恢复不会重复创建。
\shot[0.25\textheight]{18-school-mapping}{本站后台确认学校全称、简称、国家及远端组织编号。}
\shot[0.28\textheight]{19-domjudge-organizations}{实际 DOMjudge 组织列表：确认学校全称、简称和国家信息。}

\textbf{字段映射与验收。}中文队名写入队伍 \code{name} 与 \code{display_name}。DOMjudge 9.0.1 将成员名单保存到公开说明字段，因此英文队名与成员姓名合并写入 \code{public_description}，同步后读取该字段核验两者完整保存。学校映射到组织，队伍 ICPC 编号、编号／座位、地点为可选基础字段。账号填写队名／姓名和队长联系人邮箱，角色固定 team；远端 ID、独立用户名和密码由系统管理。完整流程为学校 → 队伍 → 账号绑定队伍 → 实际登录并确认目标比赛访问。
\shot[0.30\textheight]{20-domjudge-team}{实际 DOMjudge 队伍信息：组织、分组与比赛账号关联。}

新远端队伍 ID 按“绑定＋报名”生成，历史映射复用原 ID。跨比赛共享同一历史队伍的映射会暂停更新并提示管理员处理。队伍编号／座位在 DOMjudge 中全局唯一，填写时避免与其他比赛已有队伍重复；冲突会明确显示占用队伍。修改学校、队名、参赛性质或人员后重新审核，新同步更新队伍资料；DOMjudge 9.0.1 的用户更新接口存在限制，账号名称或邮箱变化会明确列出需人工更新的差异。请在远端账号后台修改资料后重新发起同步。

\begin{itemize}
\item 401／403：检查 API 账号启用状态及 reader／writer 角色；参赛账号使用独立凭据。
\item 队伍导入后看不到比赛：检查激活时间、比赛允许组、队伍分组与比赛访问限制；创建队伍的写接口 URL 不能单独证明其已被比赛允许。
\item 学校或分组读回不符：重新查询外部 ID 并确认映射，不能仅凭 POST 成功判断完成。
\item 中途失败：任务保留已有队伍与账号编号，修正原因后按当前版本同步。若配置已改变，重新发起同步；旧任务不能覆盖新配置。
\end{itemize}
字段和分组规则参见\href{https://github.com/DOMjudge/domjudge/blob/9.0.1/doc/manual/import.rst}{9.0.1 官方导入格式}及\href{https://github.com/DOMjudge/domjudge/blob/9.0.1/doc/manual/scoring.rst}{官方分组排名说明}。

\section{比赛绑定与报名同步}
可先开放报名并完成审核、缴费，后期再启用活动的“评测平台联动”。在“外接平台中心”的“比赛绑定与报名同步”区域选择本站竞赛，再选择已获授权且启用的评测实例，填写目标比赛编号。Hydro 还需填写域编号；DOMjudge 配置正式和非正式分组，并确认学校映射。
\shot[0.48\textheight]{09-contest-binding}{绑定示例：本站竞赛关联目标比赛，并设置自动同步。}

\begin{itemize}
\item 自动同步：报名资料、人员与老师关联、审核和确认净收款满足要求后派发任务。新建或保存启用的自动同步绑定时，补同步已有合格报名；后续取得资格的报名继续自动同步。
\item 手动同步：在绑定列表点击“同步已有报名”批量同步或重试；也可在具体报名的“比赛账号”页逐条使用“同步比赛账号”。停用的绑定或实例不能发起批量同步。
\item 失败重试：查看任务原因，修正配置后重试；重复执行不会重复建立本站已映射的比赛账号。
\end{itemize}
本站账号和 OJ 比赛账号独立管理。资料或净收款变化导致本站资格失效时，停止向用户交付原比赛账号；当前适配器不支持自动停用远端账号，管理员需在评测系统内处理已有账号。

\section{配置报名字段}
\textbf{按时间审核。}每个活动从 1 开始按首次成功提交的先后分配报名编号。草稿没有编号；并发提交不重号；补正与重新提交保留原编号与首次提交时间。取消后永久删除报名，财务独立保留，原编号不重复使用。名单 CSV 为每位有效成员一行，每个成员、队伍、报名和老师字段各一列；团队金额仅填写在该报名第一行，单位为元。

\section{发票申请与审核}
参赛者在报名“财务”页提交完整开票表单，先查看可开票余额并确认信息。抬头分个人、企业、非企业单位；默认仅普通发票，管理员在竞赛费用配置中开启专用发票并选择额外必填资料。
