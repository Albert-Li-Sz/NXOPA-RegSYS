## BUG-01：冲正后无法用真实参考号更正入账

**位置**：`apps/server/src/finance.ts:398–435`，关联 `finance.ts:366–378` 和 `schema.prisma` 中 LedgerEntry 的两个参考号唯一约束。

复现步骤：

1. 同一活动创建两份付费报名 A、B，审核通过。
2. 把参考号为 `AUDIT-REFERENCE-ONE` 的 100 元收款确认到 A。
3. 由另一名财务管理员冲正该收款，A 净到账恢复为 0。
4. B 提交使用同一真实参考号的新凭证，再确认到账。

实际结果：第 4 步触发 Prisma `P2002` / PostgreSQL `23505`，冲突约束为 `LedgerEntry_contestId_channelReference_key`；B 净到账仍为 0。即使更换渠道，`normalizedReference` 仍有独立唯一约束。

原因：冲正只新增负数分录并更新余额，没有调整原收款对参考号的占用。原凭证也仍然是 CONFIRMED，不能通过重新审核完成归属纠正。

建议：明确区分不可变的历史参考号与当前有效收款的唯一占用，在同一事务内撤销被冲正款项的有效占用。保留原账簿、凭证和审核记录，并验证“冲正后正确入账”和“未经冲正不能重复入账”两个方向。

## BUG-02：保存与提交报名存在确定的锁顺序冲突

**位置**：`apps/server/src/registrations.ts:747–757`、`registrations.ts:921–922`。活动配置保存也采用“活动锁 → 排考锁”的顺序，见 `registrations.ts:359–362`。

当前顺序：

- 保存报名：报名锁 → `seating:<contestId>` → 活动锁。
- 提交报名：报名锁 → 活动锁 → `seating:<contestId>`。

复现步骤：同一活动准备两份不同报名，用事务屏障让提交方持有活动锁；保存方取得排考锁并等待活动锁；然后让提交方继续申请排考锁。

实际结果：调用真实 RegistrationService 方法，在隔离 PostgreSQL 中得到 `P2010`，底层错误为 `40P01: deadlock detected`；两个操作中一个失败、另一个完成。HTTP 异常过滤器会把该 Prisma 错误返回为 400“操作无法完成”，没有事务重试。

建议：统一活动、报名、排考、凭据等关联操作的锁顺序，并检查活动配置保存和删除等路径。回归应覆盖不同报名的并发保存/提交，不能只覆盖同一报名的版本冲突。

## BUG-03：已提交的个人附件导致管理员审核失败

**位置**：`apps/server/src/registrations.ts:1127–1149`，审核复用校验的入口在 `registrations.ts:1173–1177`。

触发条件：通过报名 API 把本人 `purpose=PERSONAL` 的附件 ID 填入文件字段。本项针对后端支持的附件引用路径，未声称普通报名表直接上传附件都会触发。

复现步骤：

1. 活动增加必填文件字段。
2. 报名者上传个人附件，把 ID 填入字段并保存、提交。
3. 管理员审核通过。

实际结果：报名提交成功，`TeamFile` 已存在该附件与报名的关联；管理员审核却返回 403“附件不属于此报名”。

原因：首次提交只给 PRIVATE 文件补充 `registrationId`；PERSONAL 文件保留空 `registrationId`，通过 TeamFile 建立关联。再次验证时没有认可该关联，而是要求当前调用者拥有文件。审核时调用者已变成管理员。

建议：统一附件归属判断，认可当前报名已建立的有效关联，同时保留跨报名、已删除、公开文件和工单附件的限制。增加“报名者提交、另一账号审核”的跨角色回归。

## BUG-04：额外到账使仍然有效的准考证从选手端消失

**位置**：`apps/server/src/finance-accounts.ts:62–68`、`apps/server/src/admissions.ts:182–185`、`admissions.ts:608–621`，关联 `registrations.ts:177–188`。

复现步骤：

1. 应收 100 元的报名审核通过并足额到账，取得参赛资格。
2. 为当前报名版本准备已发放的准考证记录，确认 `AdmissionService.mine` 能列出它。
3. 再确认一笔 1 元的额外到账。

实际结果：报名依然 `eligible=true`，证件依然 `state=RELEASED`，但报名版本由 4 增为 5、文档记录仍对应版本 4。“我的准考证”不再列出该证件，下载接口同样因版本不同而拒绝。没有自动重新生成任务。

原因：余额变化无条件增加报名版本，证件的可见性与下载要求版本完全相同；资格未变时，`refresh` 又不会把证件标为 STALE，造成状态与实际可用性不一致。

建议：区分影响证件内容的资料版本与财务记录版本。若业务确实要求财务变动后重新生成，至少同步标记失效并明确提示/安排重发，避免保留“已发放”的状态却无法下载。

验证边界：本项以数据库中的 RELEASED 文档记录作为前置条件，验证版本、资格和列表逻辑；没有执行 LaTeX 编译或检查 PDF 内容。

## BUG-05：纯空白姓名和必填文本可以提交

**位置**：`apps/server/src/registrations.ts:1483`、`registrations.ts:1120–1126`。

场景 A：调用成员资料修改接口，把姓名设为三个空格，然后重新提交。`personAnswers` 只有 `min(1)`，没有普通报名保存 schema 中的 `trim()`；提交检查的是账户资料完整性，没有重新拒绝空白成员姓名。

场景 B：为活动配置必填文本字段，把值设为三个空格后提交。校验只拒绝空字符串和空数组，没有拒绝纯空白字符串。

实际结果：两个场景都成功提交；在关闭人工审核的活动中均得到 `review=APPROVED`、`eligible=true`。场景 A 的持久化成员姓名确实为三个空格。

建议：对姓名复用统一的 trim + 非空 schema；对必填文本按去除首尾空白后的内容判空，保持数字 0 和布尔值 false 的合法性。
